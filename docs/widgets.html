Custom widgets

The shared blocks every Velocity Suite application uses, what they take and when to use them. Build each once and reuse it; don’t change one for a single screen. Each is styled only with the shared app-* classes on the Theme page, listed under it. The button blocks are on the Button standard.

Carried over from LifeView

General enough to reuse, adapted for Velocity Suite.

DateFormat

Every date shown as text: list columns, record headers and detail screens.

  • Inputs: Date (DateTime, mandatory), ShowTime (Boolean, default False), ExtendedClass.
  • Shows: MM/dd/yyyy (“08/25/2026”), or “08/25/2026 09:12” with ShowTime, never wrapping. Blank for a null date (OutSystems’ null date is 01/01/1900): no N/A, no placeholder date.
  • The same format as LifeView. The mockups’ “Aug 25, 2026” style isn’t used.

Classes: none of its own. The parent passes app-value or app-text through ExtendedClass.

RecordHeader (LifeView’s StickyPageHeader)

The persistent header of every record workspace: “context before forms”. It stays in view while the page scrolls, so the record and its buttons are always visible.

  • Inputs: RecordNumber, Title, Status, Severity, Owner, and a Fields list of the key identifiers (part, lot, supplier, work order, related Quality Event). Optional BackLabel (blank = “Back”).
  • Placeholder: Buttons, for the header buttons as the Button standard places them.
  • Event: BackClicked.
  • Uses StatusBadge for status and severity.

Classes: app-page-header, app-back, app-actions, app-label, app-value

ButtonApply / ButtonClear (LifeView’s ButtonSearch / ButtonReset)

The two filter-panel buttons, renamed to the mockups’ labels. Same inputs as the other button blocks; no logic of their own.

Classes: app-btn app-btn-primary, app-btn app-btn-outline

The button block pattern and the table class

  • Every button block uses app-btn plus one variant, takes IsEnabled and ExtendedClass and raises Clicked. See the Button standard.
  • Every list table gets one theme class (LifeView’s app-table): header in the theme’s accent color, row striping, and app-icon-link row actions.

New for Velocity Suite

The reusable components the UI/UX specification lists, plus two the screens need. All are planned: inputs will firm up as the screens are built.

StatusBadge

Every status and severity: a colored pill (Draft, Investigation, Closed; Low, Medium, High, Critical). Inputs: Label, Kind (status / severity / hold). Also draws the HOLD, SHIPPED and CUSTOMER markers on lots (BR-006).

Classes: app-pill, app-pill-info, app-pill-success, app-pill-warning, app-pill-danger

The block maps each status to a variant, so a screen never picks pill colors itself.

WorkflowStepper

A record’s lifecycle with the current step highlighted, from its status list. Replaces the app’s four separate status wizards (CAPA, NCR, MRB, SCAR), which don’t refresh when their input changes and use a deprecated pattern. Inputs: Steps list, CurrentStep.

Classes: app-step-done, app-step-current, app-step-pending, app-step-name

ActivityTimeline

The chronological history on every record (Quality Event, NCR, MRB, CAPA, SCAR): “09:21 – Lot RM48-9817 placed on hold”. Reads the AuditLog. Inputs: EntityType, RecordId.

Classes: app-list-stack, app-list-row, app-rule

Attachments

Upload, download and preview evidence with a category and description. Drag and drop; JPG, PNG, PDF, XLSX, DOCX. Inputs: EntityType, RecordId, IsReadOnly.

Classes: app-dropzone, app-upload-row, app-attach-table, app-icon-link-danger

ActionList

The common action-assignment interface: a record’s actions with owner, due date, priority and status, plus add, start, complete and verify. Used on every record and on My Work. Inputs: EntityType, RecordId.

Classes: app-table, app-pill, app-icon-warn (overdue)

ApprovalPanel

Approvers with their decision, date and comment, and Approve / Reject / Request Information for the current user. Comment required to reject. Used by MRB decisions, CAPA action plans, hold release and closures.

Classes: app-card app-card-sm app-stack, app-list-row, app-btn

RelatedRecords

Cards for a record’s linked Quality Event, NCRs, MRBs, SCARs and CAPAs, each with its status. Clicking one opens it, so users move between related records without going home.

Classes: app-card app-card-sm, app-link, app-pill

ImpactSummary

The affected quantities for a suspect lot: affected, on hold, consumed, shipped, customers exposed. Known defective kept separate from suspect. Used on the Quality Event Impact tab, Lot Trace and MRB.

Classes: the app-kpi family, app-grid app-cols-4

AI assistant and agents

AIAssistantPanel

The collapsible right-side panel on a record. Phase 1: Summarize, Find similar events, Suggested next steps. Every suggestion carries Accept and Dismiss; nothing applies until a person accepts it. Inputs: EntityType, RecordId.

Classes: app-split-side, app-panel-info, app-card app-card-sm

Agent hooks Coming soon

Later phases add agents that gather information, coordinate investigation work, watch overdue actions, prepare summaries and recommend next-best actions, with a person reviewing at defined control points. To leave room for them now:

  • The assistant panel gets an Agent activity section, so what an agent did shows next to what it suggests.
  • Agent work is written to the same ActivityTimeline and ApprovalPanel as people’s, marked as an agent, so the audit trail stays complete.
  • Agents act only through the same workflow actions as users, never by changing a status directly.

Not carried over

  • CodeTableDropdown, IncentiveCodeDropdown, CodeTableText: built on the LifeView gateway’s code tables. Velocity Suite lookups are OutSystems static entities and reference data, so standard dropdowns do the job.
  • EffectiveDateFilter: specific to LifeView’s effective-dated payroll lists.
  • CodeDescriptionConcat: not needed while lookups have a Label. Worth bringing back if defect codes show as “DIA-HIGH - Diameter high”.
  • APIPagination: lists read from OutSystems aggregates use the standard OutSystems pagination. It could return once lists come from ERP or MES APIs through the integration layer.
